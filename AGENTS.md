# Kladit Agent development

These rules apply throughout this repository. Respond to the user in Russian unless they request another language.

## Context and architecture

- Read affected code, callers, tests and relevant docs before editing. Setup, installation and releases: [README.md](README.md). Wire contracts and metric semantics: [docs/PROTOCOL.md](docs/PROTOCOL.md). Check both against implementation and CI; fix affected stale descriptions instead of copying documentation here.
- Use the Go version floor in `go.mod` (currently 1.25.0). Keep one Linux-first CLI, built without CGO for Linux amd64/arm64. Prefer the standard library; the module currently has no external Go dependencies. Add dependencies or raise the Go floor only for a demonstrated task requirement.
- Keep CLI wiring/exit behavior in `cmd/kladit-agent`, collection/parsing in `internal/metrics`, transport/enrollment in `internal/connection`, and local permissions in `internal/policy`. Reuse suitable functions before adding new ones. Add interfaces, goroutines or packages only when they clarify a real responsibility; avoid service/repository layers and framework-driven rewrites.
- Preserve the oneshot CLI plus systemd timer model. Metrics collection and outbound delivery do not require a listener, worker queue, database, gRPC, Kubernetes or a scheduler. New remote-execution capabilities require an explicit task and local-policy design; do not add them speculatively.
- Substantial refactoring is allowed to correct demonstrated architectural errors, duplication, security problems or needless complexity. Prefer the resulting architecture over the smallest diff, explain the benefit, and keep necessary related restructuring together. Avoid cosmetic churn and speculative abstractions; remove code proven unused by your changes.
- Preserve CLI behavior, Agent API/enrollment contracts and compatibility unless explicitly tasked otherwise. Backend ownership, token issuance/revocation and scheduling belong to Kladit; do not change the companion repository unless requested.

## Security and behavior

- Local policy is deny-by-default: missing/false permissions and invalid policy must fail closed. Keep explicit installer consent and the policy check before collection and recheck before sending. The backend must not override local policy through a response.
- Use a separate machine token, never a user session, SSH credential or shared backend secret. Keep secrets out of arguments, stdout, logs, errors and committed fixtures. Preserve private regular token files, exclusive credential creation, failure cleanup and systemd `LoadCredential`; pass enrollment secrets through stdin.
- Retain verified HTTPS, request deadlines, context cancellation, disabled environment proxies and no redirects for enrollment/metrics. Enrollment response URLs must satisfy the existing same-origin/path validation. Bound external inputs/responses and keep errors free of reflected response bodies or secrets. Do not introduce automatic retries of a single-use enrollment exchange or overwrite existing credentials.
- Keep numeric units, JSON names, null/empty/missing semantics and bounds compatible with the protocol. Preserve root filesystem disk semantics and all-GPU NVIDIA query CSV parsing. Missing/failing `nvidia-smi` yields an empty GPU array without breaking CPU/RAM/disk delivery; unavailable GPU values remain null. Do not treat host metrics as cgroup limits.
- Keep external commands bounded and cancellation-aware; pass fixed executable arguments rather than interpolating untrusted data through a shell. Keep POSIX `sh` scripts compatible with their shebangs, quote paths and clean up private staging directories.
- The installer requires root; the agent runs unprivileged with systemd hardening. Preserve the local-mode network restriction and narrowly scoped connected-mode override. Do not weaken sandbox/device access merely to make a test pass. Preserve refusal to replace an installation, explicit uninstall/purge behavior and user-owned systemd overrides.
- Checksums detect corruption, not a compromised release publisher. Preserve versioned HTTPS downloads and the release immutability checks. `cmd/kladit-agent/main.go` owns the version; do not bump it, publish releases, move tags or replace assets unless the task requests it.

## Verification and reporting

- Run checks from the root. Current commands and deployment checks live in [.github/workflows/ci.yml](.github/workflows/ci.yml) and [.github/workflows/release.yml](.github/workflows/release.yml).
- For Go changes: format changed files with `gofmt`, verify `gofmt -l cmd internal` is empty, run relevant tests, `go test -race ./...`, `go vet ./...`, and `CGO_ENABLED=0 go build -o <temporary-output> ./cmd/kladit-agent`. Race tests need a supported native toolchain/C compiler; the release binary remains CGO-free. Use actual Go tooling, not npm/Jest examples from skills.
- For shell changes, run `sh -n` on each `scripts/*.sh`. For packaging/systemd/release changes, also build temporary bundles with `sh scripts/package.sh <temporary-output-dir> https://kladit.example/agent/test` and verify them with `sh scripts/check-package.sh <temporary-output-dir> <agent-version>`. The bundle check executes the amd64 binary; use a compatible Linux host. Obtain the version from the CLI/source, not a duplicated constant.
- Installer `--check` checks prerequisites only. Full install/remove/reinstall and systemd credential/sandbox checks need a disposable Linux systemd host, as in CI; never install on the user's connected servers or alter host services merely to verify a change. GPU mocks do not prove behavior on NVIDIA hardware. Report these limits explicitly.
- Add tests for significant behavior, regressions, malformed input, cancellation, policy and secret handling. Reuse `testing`, `httptest` and temporary files. Do not add tests for document wording, implementation structure or a coverage target; do not weaken security checks or skip failures to get green results.
- For Markdown/skill-installation-only changes, check facts, local links, instruction consistency, upstream byte integrity, provenance and licenses; application/systemd tests are unnecessary. Before a PR, review the final diff and report what changed, which checks passed, and anything unverified with reasons. Do not claim unavailable checks passed.
