# Agent API v1

Клиент отправки и backend приёма метрик реализованы. Контракт отправки метрик остаётся совместимым с Agent API v1.

## Приём метрик

Маршрут: `POST /api/v1/agent/metrics`. Полный URL задаётся локально в `connection.json`.

```http
Authorization: Bearer <machine-token>
Content-Type: application/json
User-Agent: kladit-agent/<version>
```

```json
{
  "version": 1,
  "agent_version": "0.3.0",
  "metrics": {
    "collected_at": "2026-11-03T17:00:00Z",
    "cpu_usage_percent": 25,
    "memory_total_bytes": 8589934592,
    "memory_available_bytes": 6442450944,
    "memory_used_bytes": 2147483648,
    "uptime_seconds": 3600,
    "disk": {
      "total_bytes": 107374182400,
      "used_bytes": 21474836480,
      "available_bytes": 80530636800
    },
    "gpus": [
      {
        "index": 0,
        "name": "NVIDIA A100",
        "utilization_percent": 25,
        "vram_total_bytes": 42949672960,
        "vram_used_bytes": 1073741824,
        "temperature_celsius": 42
      }
    ]
  }
}
```

`disk` описывает файловую систему `/`. Занятый объём равен общему минус все свободные блоки, а доступный учитывает блоки, зарезервированные файловой системой. Поэтому `used_bytes + available_bytes` может быть меньше `total_bytes`. Ошибка чтения `/` завершает текущий сбор с ошибкой.

`gpus` содержит все GPU из одного запроса `nvidia-smi` в CSV. Индексы относятся к текущему порядку NVIDIA. VRAM переводится из MiB в байты. Недоступное числовое показание передаётся как `null`. При отсутствии GPU или утилиты, таймауте, отказе драйвера или некорректном CSV передаётся `[]`. Остальные метрики отправляются как обычно.

Агенты до 0.3.0 могут присылать снимок без `disk` и `gpus`. Перед подключением 0.3.0 обновите backend до версии, принимающей эти поля.

Успех: `204 No Content`. Любой другой статус считается ошибкой, тело ответа игнорируется. При `401`/`403` проверить привязку и отзыв токена; при `429`/`5xx` следующий запуск отправит новый снимок. Агент не повторяет запросы и не хранит очередь метрик. После сбоя сети результат предыдущего запроса может быть неизвестен.

## Требования к backend

- Отдельная аутентификация агентов. Общий `X-Auth-Backend-Secret`, пользовательские cookies и SSH-пароль агенту не передаются.
- Уникальный случайный токен на машину, минимум 32 случайных байта; например base64url. В БД хранится hash токена и связь с сервером/владельцем. По токену backend определяет машину; machine ID из запроса не используется для авторизации.
- Проверять отзыв токена при каждом запросе. Удаление/отвязка сервера отзывает его credentials. Ротация и отзыв выполняются backend, новый файл токена устанавливается локально.
- Проверять схему и размеры. Размер тела до 16 KiB, `version=1`, CPU и загрузка GPU от 0 до 100. Для RAM общий объём равен сумме занятого и доступного. Для диска сумма занятого и доступного не превышает общий объём. Занятая VRAM не превышает общий объём, если оба показания доступны. Время приёма хранить отдельно от времени агента.
- Не писать Authorization и тело запроса в логи. Применить rate limit на машину. Ответ не содержит команд или policy.

## Установка и привязка

Основной сценарий начинается в кабинете: пользователь выбирает сервер и разрешения. Backend создаёт короткоживущую одноразовую заявку установки, привязанную к пользователю и серверу. Один установочный комплект запускается либо через SSH после проверки host key, либо вручную владельцем.

Enrollment обменивает одноразовую заявку на machine credentials; установщик не должен получать общий секрет backend или сохранять пароль аккаунта. Одноразовые коды нельзя использовать как постоянный токен метрик. Приватный ключ для будущей proof-of-possession identity генерируется на самой машине.

Установщик поддерживает enrollment и прежний режим готового machine-токена из файла. mTLS и SSH-установка из кабинета пока не реализованы. Долгоживущий bearer-токен, украденный с машины, позволяет отправлять метрики от её имени до отзыва; текущий transport не является proof-of-possession identity.


## Enrollment v1

Backend Kladit принимает метрики и machine credentials после PR #15. Enrollment заменяет ручную передачу постоянного токена пользователю.

Владелец вызывает `POST /api/v1/servers/:id/agent-enrollment` с пользовательской сессией. Ответ 201: `{installCommand, expiresAt}`. Команда содержит одноразовый секрет и действительна 10 минут. Новая заявка отменяет предыдущую незавершённую; действующий агент работает до успешного обмена. `DELETE` этого маршрута отменяет только заявку. Отзыв агента отменяет также незавершённый enrollment; удаление сервера удаляет обе записи.

Установщик запускает `kladit-agent enroll --url https://HOST/api/v1/agent/enroll --directory PRIVATE_DIR`, передавая одноразовый секрет через stdin.

```http
POST /api/v1/agent/enroll
Authorization: Bearer <one-time-enrollment-token>
Content-Type: application/json

{"version":1}
```

Ответ 201 (не логировать):

```json
{"version":1,"machine_token":"<32 random bytes, base64url>","metrics_url":"https://HOST/api/v1/agent/metrics"}
```

401: токен неизвестен, просрочен, отозван или уже использован. 429: ограничение частоты. Backend блокирует запись сервера, проверяет TTL по своим часам, удаляет заявку и ротирует machine credential одной транзакцией. При конкурентных обменах успешен ровно один запрос. В БД только SHA-256 обоих секретов. Server/user не принимаются от агента.

Агент требует проверенный HTTPS без redirect/proxy и принимает metrics_url только того же origin. Ответ ограничен 4 KiB. Machine token записывается с mode 0600, существующие credentials не перезаписываются. Если ответ потерян или локальная запись не удалась, запрос не повторяется: пользователь создаёт новую заявку. Локальные policy/connection/token создаются установщиком, далее используется прежний `send` и systemd timer.

Ручной и будущий SSH-bootstrap используют один `scripts/bootstrap.sh` из собранного комплекта. SSH передаёт тот же enrollment через stdin, не меняя API и жизненный цикл. Автоматическая SSH-доставка пока не реализована. Bearer identity не является proof-of-possession.
